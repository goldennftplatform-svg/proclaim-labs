## API overview

### `wallet-types`

All types derive `Debug + Clone + PartialEq + Serialize + Deserialize`.

* IDs/newtypes: `AccountId`, `KeyHandle`, `DappId`, `SessionId`, `ProgramId`,
  `RequestId`, `ActorId`, `Mint`, `ZoneId`, `ApprovalToken`.
* Domain: `AccountKind`, `Capability`, `Asset`, `TransactionRequest`,
  `ProgramMeta`, `VerificationStatus` (the five plan variants), `ApprovalGrant`,
  `AssetMovement`, `SimulationResult`, `EffectsSummary`, `ApprovalState`,
  `SignedTransaction`, `SubmissionReceipt`.
* Errors: `Denied`, `RegistryError`, `IdlError`, `KeystoreError`, `WalletError`
  (all implement `Display`/`std::error::Error`).
* `EffectsSummary::to_human_lines()` renders the request dApp, account/zone,
  program name/version/author, asset/amount/destination, approvals granted and
  moved, the **unlimited-approval** flag, gas/fee fields, verification badge,
  warnings and a raw-calldata fallback. This is the human-readable prompt shape
  from plan section 3.3.
* `hexutil::{encode, decode}` is a tiny local helper (no `hex` dependency).

### `wallet-keystore`

`EncryptedKeyStore` with `create(path, passphrase)`, `unlock(path, passphrase)`,
`lock()`, `is_unlocked()`, `list_keys() -> Vec<KeyInfo>`,
`import_key(label, [u8; 32])`, `generate_key(label)` and
`sign(&KeyHandle, message) -> Vec<u8>`.

Real cryptography (via `sodiumoxide` 0.2.7 / system libsodium 1.0.18):

* `crypto_pwhash_scryptsalsa208sha256` (interactive limits) derives a 32-byte
  master key from the passphrase and a per-store random salt; the salt and a
  sealed constant are stored so a wrong passphrase is detected at unlock.
* `crypto_secretbox_xsalsa20poly1305` encrypts each 32-byte Ed25519 seed under a
  fresh random nonce. The JSON file contains only version, salt, nonces,
  ciphertexts and **public** keys — no plaintext seed, no `"seed"` field.
* `crypto_sign_ed25519` detached signatures are produced by `sign()`; the
  public key from the seed is stored so the UI can show it while locked.
* `lock()` zeroizes every in-memory seed and the master key; `Drop` calls
  `lock()`. Writes use a sibling `.tmp` file plus `rename` (atomic on Unix).

Test `on_disk_bytes_do_not_contain_key_material` reads the file back and asserts
it contains neither the raw 32-byte seed nor its hex encoding.

### `wallet-core`

Four adapter traits, all mockable:

* `ProgramRegistry::{resolve, verification_status}` (LP-0023 boundary);
* `IdlProvider::decode_and_simulate` (PR #188 `lez-idl` boundary);
* `CoreAuthorizer::approve` (policy/user-approval check);
* `Signer::{sign, submit}`.

`WalletCore::{new, propose_transaction, effects_preview, state, reject,
authorize, sign_and_submit}` implement the state machine:

```
Proposed -> AwaitingApproval{effects}
         -- authorize() only, via CoreAuthorizer --> Approved{effects, token}
         -- sign/submit via Signer --------------> Signed -> Submitted
Rejected / Failed are terminal for signing.
```

`wallet_proposeTransaction` resolves registry metadata, decodes/simulates via
the IDL, and builds `EffectsSummary` with a verification status. A failed
registry or IDL lookup degrades gracefully: the request still reaches
`AwaitingApproval` with warnings, `effects_available = false`, the badge
`Unregistered` and the raw calldata — **never** `Approved`. Only
`WalletCore::authorize` sets `Approved`, and only `Approved` allows
`sign_and_submit` to reach the signer. Capability, session and fee-payer checks
are enforced there too.

Mock implementations (`MockRegistry`, `MockIdl`, `MockAuthorizer`, `MockSigner`)
are compiled into the library so downstream tests can reuse them. `MockSigner`
exposes a call log used by the negative tests.

## Exact build / test commands that worked

Run in WSL on 2026-11-19 (Rust 1.100.0, `libsodium-dev` 1.0.18):

```bash
source ~/.cargo/env
export CARGO_BUILD_JOBS=2
export SODIUM_USE_PKG_CONFIG=1
unset RUSTFLAGS
cd /mnt/c/Users/XPS/Downloads/GFD/staged/lp0021-phase0
cargo test --workspace
# or simply: bash ./run-tests.sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
```

Results: **23 tests passed** (wallet-core 12, wallet-keystore 6, wallet-types 5;
0 doc tests), `cargo fmt --check` clean, `cargo clippy -D warnings` clean.

Notes on the environment flags:

* `SODIUM_USE_PKG_CONFIG=1` is recommended. It makes `libsodium-sys` link the
  installed system libsodium instead of building a bundled copy (the bundled
  build runs libsodium's own `make check` and took >9 minutes here). Without
  the variable, `sodiumoxide` still compiles — it is just much slower.
* `RUSTFLAGS='--cfg getrandom_backend="custom"'` is **not needed** for these
  crates. Both `cargo test --workspace` without it and with that exact global
  flag succeeded; no `__getrandom_v03_custom` linker error occurred because no
  crate here uses `getrandom`. Prefer not setting it.

## What is real vs mocked (honest scope note)

**Real:** libsodium scrypt KDF + secretbox encryption/decryption, Ed25519
signing, atomic JSON persistence, serde schemas, the approval state-machine
transitions and all enforcement checks. Every test runs locally with no network.

**Mocked / fixture-only — no chain, no testnet:**

* `MockRegistry`, `MockIdl`, `MockAuthorizer` and `MockSigner` are in-memory
  fakes. They do not call an LEZ node, sequencer, LP-0023 registry or IDL store.
* Program metadata, `image_id`/source commit, cycle counts, fees, balances and
  "destination" values are test fixtures, **not** testnet-0.4 measurements.
* `target_zone` is the literal string `lez-testnet-0.4`; no endpoint config or
  chain interaction exists. Nothing here fabricates testnet behaviour.
* `MockSigner` returns a synthetic signature string, not a real chain
  transaction hash; real signing would wrap `wallet-keystore` and a chain client.
* Not included here (later phases): provider SDK/JSON-RPC + TS client, Qt/QML UI,
  `wallet-chain`/`wallet-token`, funding adapter, Logos Storage, release
  integrity, on-chain `testimonial_store`, adoption evidence.

Mapping to the plan: implements Phase 0 action (b) (section 4) and the approval
flow / adapter boundaries of architecture sections 3.1–3.4, especially decision
3 (approval enforced in the core module), the `EffectsSummary` shape in 3.3,
graceful degradation in 3.4 step 6, and reliability criterion R2.
