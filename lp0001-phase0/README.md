# LP-0001 Phase 0 — NFT Wallet Support and Private Ownership Proof

Self-contained Rust Cargo workspace defining the **contracts and deterministic
host-side fixtures** for LP-0001.

> **Honesty notice:** This phase contains no real zero-knowledge proof, no
> RISC Zero circuit, no LEZ program, no testnet deployment, no wallet, and no
> NFT program. `MockBackend` is explicitly a test fixture, not a ZK backend.
> No privacy is achieved by this code. See
> [`crates/membership-proof/STATEMENT.md`](crates/membership-proof/STATEMENT.md).

## Required guarantees expressed in this phase

- Proof reveals membership in a collection without exposing which token or
  which account: `ProofPackage` contains only public inputs, proof bytes and
  plain-language disclosure strings.
- Context binding via `gate_context_hash`; different gate contexts produce
  different nullifiers and a proof for one context fails in another.
- Freshness via a per-token sequence registry: a newer issue sequence
  supersedes every earlier proof even when ownership did not change.
- Replay resistance via nullifier uniqueness and an authorize/reject/consume
  state machine with replay blocked.
- Proof-request capability stands alone: `request_proof()` requires only
  `NftCapability::ProofRequest`; it never calls the account provider or signer
  and never requires `AccountAccess`.
- Deterministic error taxonomy (`NotMember`, `MalformedProof`, `Expired`,
  `ContextMismatch`, `Superseded`, `Unsupported`) with a fixed check order:
  scheme/format → context → expiry → supersession → membership → nullifier.
- Mock host verifier and simulated LEZ verifier share one `evaluate()`
  function, so the parity tests assert identical outcomes for identical bad
  inputs.

## Honest limitations

1. **No real ZK.** `MockBackend` and `SimulatedOnChainBackend` are fixtures;
   the mock proof is a domain-separated byte string with a token handle, not a
   proof. It provides no soundness and no zero-knowledge hiding.
2. **No actual privacy claim.** The token handle is a stable pseudonym and
   could be linkable. Only the designed RISC Zero statement, once built and
   audited, could support a privacy claim.
3. **No LEZ / testnet / on-chain verifier.** The "on-chain" path is a Rust
   function simulating the same deterministic checks.
4. **No wallet, no NFT program.** `AccountRef` is an opaque handle; no real
   wallet connection, signing key custody or collection program exists.
5. **No deployed freshness authority.** The freshness registry is in-memory
   fixture state, not a chain-backed counter.
6. **Trusted setup:** none planned for the intended RISC Zero deployment, but
   nothing is deployed and no ceremony/deployment guarantee is asserted here.
